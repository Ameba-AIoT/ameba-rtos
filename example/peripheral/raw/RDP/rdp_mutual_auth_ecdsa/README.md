# rdp_mutual_auth_ecdsa

A TrustZone-protected **ECDSA P-256 mutual mTLS** client example.

- The client ECDSA private key lives in **Secure World (image3)** and never enters NS-side memory.
- TLS CertificateVerify signing is routed from the NS-side mbedtls TLS state machine to the
  S-side via a custom `mbedtls_pk_info_t` and an NSC (Non-Secure Callable) interface.
- Forced cipher suite: `TLS-ECDHE-ECDSA-WITH-AES-128-GCM-SHA256`.
- The server is a companion Python script running on a PC in the same LAN as the board.

## Certificate System and Handshake

### Certificate system (generated by gen_certs.sh)

`gen_certs.sh` creates a self-signed PKI. Each party holds different material:

```
gen_certs.sh output:

  ca.key ──signs──► ca.crt (self-signed root CA)
      │                │
      │ issues         │ issues
      ▼                ▼
  server.key        client.key
  server.crt        client.crt
  (server identity) (client identity)
  SAN=<SERVER_IP>

Material distribution:
  ┌──────────────────┬──────────────────────┬────────────────────────┐
  │  Firmware S-side │  Firmware NS-side     │  Server PC             │
  │  (image3)        │  (example .c)         │  (ecdsa_mtls_server.py)│
  ├──────────────────┼──────────────────────┼────────────────────────┤
  │ d from client.key│ client.crt (identity) │ server.crt + server.key│
  │ client.crt PEM   │ ca.crt (verify server)│ ca.crt (verify client) │
  │ (key never leaves│                       │                        │
  │  S-side)         │                       │                        │
  └──────────────────┴──────────────────────┴────────────────────────┘
```

### Full handshake (TLS 1.2 ECDHE-ECDSA)

```
  Board NS-side             Board S-side            Server PC
  (mbedtls TLS client)    (image3 / NSC)        (ecdsa_mtls_server.py)
       │                       │                       │
       │  ── Pre-handshake setup ───────────────────── │
       │                       │                       │
       │  secure_ecc_client_init()                     │
       │ ──────────────────────►│                       │
       │  ◄── client.crt PEM ───│                       │
       │  (NS receives cert;    │                       │
       │   private key d stays  │                       │
       │   on S-side)           │                       │
       │                       │                       │
       │  ── ① ClientHello ──────────────────────────► │
       │    Propose TLS 1.2 + ECDHE-ECDSA-AES128-GCM   │
       │                       │                       │
       │  ◄─ ② ServerHello ──────────────────────────  │
       │    Confirm cipher suite, generate server random│
       │                       │                       │
       │  ◄─ ③ Certificate ──────────────────────────  │
       │    Payload: server.crt                         │
       │    NS validates server.crt against ca.crt      │
       │    → Server identity confirmed ✓               │
       │                       │                       │
       │  ◄─ ④ ServerKeyExchange ───────────────────── │
       │    Payload: ECDHE ephemeral public key          │
       │           + signature by server.key            │
       │    NS verifies signature using server.crt pubkey│
       │    → ECDHE params not tampered ✓               │
       │                       │                       │
       │  ◄─ ⑤ CertificateRequest ──────────────────── │
       │    Server requests client certificate          │
       │    (triggers mutual authentication)            │
       │                       │                       │
       │  ◄─ ⑥ ServerHelloDone ──────────────────────  │
       │                       │                       │
       │  ── ⑦ ClientKeyExchange ───────────────────── ►│
       │    Payload: client ECDHE ephemeral public key   │
       │    Both sides compute PreMasterSecret (ECDH)    │
       │    → Derive MasterSecret                       │
       │    → Generate client_write_key / server_write_key│
       │      (AES-128-GCM session keys, this session only)│
       │                       │                       │
       │  ── ⑧ Certificate ──────────────────────────► │
       │    Payload: client.crt                         │
       │    Server validates client.crt against ca.crt   │
       │    → Client identity confirmed ✓               │
       │                       │                       │
       │  ── ⑨ CertificateVerify ───────────────────── ►│
       │    Proves client holds private key for client.crt│
       │                       │                       │
       │   mbedtls_pk_sign()   │                       │
       │  ──────────────────── ►│                       │
       │   Input: handshake     │                       │
       │   transcript hash      │                       │
       │   (SHA-256, 32 bytes)  │                       │
       │                       │  secure_ecc_client_sign()
       │                       │  Signs hash with s_cli_d│
       │                       │  ECDSA P-256 signature  │
       │                       │  → DER-encoded (~71 B)  │
       │  ◄── DER signature ─── │                       │
       │  (key d never left S-side)                     │
       │                       │                       │
       │  CertificateVerify payload = DER signature above│
       │ ────────────────────────────────────────────── ►│
       │                       │  Server verifies sig    │
       │                       │  using client.crt pubkey│
       │                       │  → Mutual auth done ✓   │
       │                       │                       │
       │  ── ⑩ ChangeCipherSpec + Finished ──────────► │
       │  ◄─ ChangeCipherSpec + Finished ────────────── │
       │    Both sides verify Finished with session keys │
       │    → Handshake integrity confirmed ✓           │
       │                       │                       │
       │  ◄══════════════════════════════════════════  │
       │       AES-128-GCM encrypted application data   │
       │  ══════════════════════════════════════════►  │
```

### Relationship between ca.crt, client.crt, and client.key

```
  ca.key (kept offline; lock away after cert issuance)
      │
      │ ECDSA-SHA256 signature over TBSCertificate:
      │   SerialNumber / Issuer / Validity /
      │   Subject: "RTK Board Client" /
      │   SubjectPublicKeyInfo: 04:8d:58:f4:... (client public key) /
      │   Extensions: clientAuth
      │
      ▼
  client.crt
  ┌──────────────────────────────────────────────────────┐
  │ Issuer  : RTK Demo Root CA                           │
  │ Subject : RTK Board Client                           │
  │ Public Key: 04:8d:58:f4:f5:81:77:b9:... (65 bytes)  │← CA endorses this key
  │ Signature : 30:45:02:20:2e:ed:58:...  (by ca.key)   │← tamper-proof
  └──────────────────────────────────────────────────────┘
         │ mathematically paired (keypair)
         ▼
  Private scalar d from client.key (32 bytes, stored in firmware S-side)
  s_cli_d[32] = { 0xXX, 0xXX, ... }   ← generated by gen_certs.sh, unique each run

  Server-side verification logic:

  Server receives client.crt
      │
      ├─① Read Issuer = "RTK Demo Root CA" from client.crt
      ├─② Locate ca.crt in trust store, extract CA public key
      ├─③ Recompute SHA-256(TBSCertificate)
      └─④ Verify Signature Value with CA public key
              │
              ▼ Pass ✓
          The client public key in client.crt was written and
          signed by the CA — it has not been tampered with.
          → ca.crt "vouches" for this public key
          → But does not prove the sender holds the private key

  Board sends CertificateVerify
      │
      └─ Sign full handshake transcript with s_cli_d → DER signature
         Server verifies with public key from client.crt
              │
              ▼ Pass ✓
          The sender holds the private key paired with client.crt
          → The sender IS the CA-approved RTK Board Client ✓

  Combined conclusion:
  "This device holds a CA-trusted certificate AND is its rightful owner."
```

### Certificate and key usage per handshake step

| Step | Message | Sender | Material used | Purpose |
|---|---|---|---|---|
| Setup | `secure_ecc_client_init` | S-side → NS-side | `s_cli_d` (S-side key), `client.crt` PEM | Load S-side key; NS receives client cert |
| ③ | `Certificate` (server) | Server → Board | `server.crt` | Server presents its identity certificate |
| ③ | Verify | Board NS-side | `ca.crt` (embedded in firmware) | Verify `server.crt` signature against root CA |
| ④ | `ServerKeyExchange` | Server → Board | `server.key` (sign ECDHE params), `server.crt` (verify sig) | Deliver ECDHE ephemeral key, prevent MITM |
| ⑦ | `ClientKeyExchange` | Board → Server | Both sides' ECDHE ephemeral keys | Derive PreMasterSecret → AES-128-GCM session keys |
| ⑧ | `Certificate` (client) | Board → Server | `client.crt` (from S-side) | Client presents its identity certificate |
| ⑧ | Verify | Server | `ca.crt` (server holds) | Verify `client.crt` signature against root CA |
| ⑨ | `CertificateVerify` (sign) | NS-side → S-side → Server | `s_cli_d` (S-side, via NSC) | S-side signs handshake hash to prove key ownership |
| ⑨ | Verify signature | Server | `client.crt` (contains pubkey) | Verify DER signature — **the key step of mutual auth** |
| ⑩ | `Finished` | Both directions | `client/server_write_key` (ECDHE-derived) | Verify handshake integrity against tampering |

## Step 1: Determine the server IP

The server script runs on a PC in the **same LAN** as the board; the board connects directly
over WiFi.

Query the server PC's WiFi IP:

```bash
# Linux / macOS
ip addr show   # or: ifconfig

# Windows PowerShell
ipconfig
# Look for "IPv4 Address" under the wireless adapter (Wi-Fi)
```

Record this as `<SERVER_IP>`; it is used in several later steps.

> The board and server PC must be connected to the **same WiFi AP** (or the same router).

---

## Step 2: Generate certificates

In a bash environment, navigate to the `server/` directory and run:

```bash
cd example/peripheral/raw/RDP/rdp_mutual_auth_ecdsa/server/
chmod +x gen_certs.sh

SERVER_IP=<SERVER_IP> ./gen_certs.sh
```

After the script completes, the following files are created in the current directory:

| File | Description | Destination |
|---|---|---|
| `ca.crt` | Self-signed root CA certificate | Server + firmware |
| `ca.key` | CA private key | **Keep local only — never distribute** |
| `server.crt` / `server.key` | Server cert and key (SAN = `<SERVER_IP>`) | Server |
| `client.crt` | Client certificate | Firmware (S-side, public info) |
| `client.key` | Client private key (raw file) | Only used to extract d; discard afterwards |
| `client_d_array.txt` | Private scalar d as C byte array | **→ S-side source file** |
| `client_crt_pem.txt` | Client cert PEM string | **→ S-side source file** |
| `ca_crt_pem.txt` | CA cert PEM string | **→ NS-side example** |

Verify the certificate chain (both should print `OK`):
```bash
openssl verify -CAfile ca.crt server.crt
openssl verify -CAfile ca.crt client.crt
```

## Step 4: Start the server

Copy the following files into the same directory on the server PC:
```
from gen_certs.sh output:  server.crt  server.key  ca.crt
from this example:         ecdsa_mtls_server.py
```

**Open the firewall port** (choose for your OS):

```bash
# Linux
sudo ufw allow 8443/tcp

# Windows PowerShell (Administrator)
netsh advfirewall firewall add rule `
    name="ECDSA mTLS 8443" dir=in action=allow protocol=TCP localport=8443
```

**Start the server**:
```bash
# Linux / macOS
python3 ecdsa_mtls_server.py --host 0.0.0.0 --port 8443

# Windows
python ecdsa_mtls_server.py --host 0.0.0.0 --port 8443
```

Expected startup output:
```
ECDSA mTLS server listening on 0.0.0.0:8443
  cipher : ECDHE-ECDSA-AES128-GCM-SHA256
  client : CERT_REQUIRED (mutual TLS)
```

## Step 5: Build and flash

> **Important:** When switching from another example, add `-p` (pristine) to force the
> build system to re-merge `prj.conf` into the Kconfig configuration. Without `-p`, the
> cached `.config` may not contain `CONFIG_IMG3_ECDSA_CLIENT_SERVICE=y`, causing a link
> error (undefined reference to `secure_ecc_client_init`).

```bash
# Build (add -p when switching from another example)
./ameba.py build -a rdp_mutual_auth_ecdsa -q -p

# Subsequent incremental builds (no -p needed)
./ameba.py build -a rdp_mutual_auth_ecdsa -q

# Flash (adjust port and remote server as needed)
./ameba.py flash -p <PORT> -b 1500000 \
    --remote-server <server_ip> --remote-password "<password>" \
    --image-dir build_RTL8720F
```

## image3 Memory Footprint (measured)

| Metric | Value | Notes |
|---|---|---|
| image3 bin (XIP Flash) | **31.7 KB** (32,480 B) | `km4tz_image3_all.bin` |
| Static SRAM | **32.4 KB** (33,197 B) | `.text` + `.data` + `.bss`; used from power-on |
| S-heap available | **31.6 KB** (32,339 B) | 64 KB SRAM partition − static SRAM |
| S-heap dynamic peak | **5.3 KB** (5,395 B) | Measured watermark; ECDSA P-256 sign operation |
| TZ_S_SIZE | **128 KB** | Build-system default; actual use 37.7 KB, ample headroom |

> built**, controlled by `CONFIG_IMG3_ECDSA_CLIENT_SERVICE=y` in `prj.conf`.  
> Other examples are unaffected; their image3 is approximately **29.8 KB** (30,528 B).

## Troubleshooting

| Symptom | Likely cause | Fix |
|---|---|---|
| `net_connect fail` | Firewall blocking port / wrong IP | Check firewall rule; verify server WiFi IP |
| `Handshake FAIL` cert error | `SERVER_HOST` does not match cert SAN | Confirm IP matches `SERVER_IP` used in `gen_certs.sh` |
| `cli_crt parse fail` | S-side cert still contains placeholder | Confirm `s_cli_cert_pem` has been replaced |
| Server reports `TLS error` | Client cert not trusted by server's CA | Confirm server holds the same `ca.crt` used to issue `client.crt` |
| Link error: undefined `secure_ecc_client_init` | `CONFIG_IMG3_ECDSA_CLIENT_SERVICE` not set | Add `-p`: `./ameba.py build -a rdp_mutual_auth_ecdsa -q -p` |

## Notes

- Every time `gen_certs.sh` is re-run, a new key pair is generated. All certificate files
  in both the firmware and the server directory must be updated together.
- `ca.key` is the CA private key. Store it securely after issuing certificates; never commit
  it to a code repository.
- `rtos_create_secure_context(2048)` must be called before any NSC call in the task.
- When switching examples, always use `-p` for a pristine build. Without it the cached
  `.config` will not contain `CONFIG_IMG3_ECDSA_CLIENT_SERVICE=y`, causing a linker error.
